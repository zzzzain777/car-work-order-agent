# Agent 任务持久化设计（阶段 1，内部能力）

## 目的与范围

只读预览目前随 HTTP 响应消失，无法恢复，也无法判断管理员看到的预览是否已因补充信息变化而过期。本阶段把任务、工单最小快照、补充信息与安全精简的预览存入 Agent 自己的 PostgreSQL；任务按管理员隔离，所有修改使用版本比较。`carSystem` 的原工单不写入任何补充字段。

本阶段只提供 Java 内部存储能力，不开放任务写入 HTTP 路由，更不开放确认或分配。浏览器 Session、Cookie、CSRF 和实时权限尚未完成写操作联调；直接开放 POST 会让网页跨站请求影响任务。现有 GET 预览仍是一次性只读结果。

## 方案取舍

- 选用与政策 RAG 共用的 PostgreSQL 连接、独立 `agent_task` 表。可跨进程恢复，且数据库条件更新能阻止两个请求同时覆盖任务。
- 进程内 Map 实现更快，但重启丢失任务；先引入 Redis 会增加系统和面试解释成本。两者都不用于本阶段。
- 任务记录管理员 ID、工单 ID、工单类型/状态/顾问 ID/更新时间的最小快照；不保存 Cookie、客户姓名、电话、工单正文。预览只保存政策来源编号与顾问编号/工作量，不保存顾问姓名或政策全文。

## 状态和版本

- 新建任务：`NEEDS_INPUT`，版本 0。
- 保存预览：按预览结果进入 `NEEDS_INPUT`、`NEEDS_REVIEW`、`READY_FOR_ADMIN_REVIEW` 或 `STALE_PROPOSAL`，版本加 1。未授权预览不保存。
- 修改门店、车型或时间：无论值是否相同，都将旧预览清空，回到 `NEEDS_INPUT`，版本加 1。提交者必须提供先前读取的版本；版本不符或管理员不符时更新 0 行。
- 这些状态都不具备分配资格。`READY_FOR_ADMIN_REVIEW` 只表示模拟证据可供人工核对，不代表管理员已经确认。

## 验收

隔离 PostgreSQL 测试证明：重建存储对象后仍能读取任务；其他管理员查不到也改不了；同一旧版本只允许一次更新；补充信息变化后旧预览为空；预览持久化不包含姓名、Cookie、客户正文；不可保存未经授权或可执行分配的结果。完整 Maven 测试保持通过。
