# 客户本人选择模拟门店

日期：2026-11-02。此阶段实现 Agent 自有任务里的客户选店，不代表真实车源、预约或工单分配。

## 浏览器流程

1. 管理员在 `agent-demo.html` 创建待分配试驾工单的 Agent 任务，将页面显示的客户选店链接交给**原工单客户本人**。
2. 客户在同一浏览器登录 `carSystem` 普通账号，打开 `customer-store.html`。页面先取得同源 CSRF 令牌，再以任务编号只读查询工单归属和当前任务版本。
3. 客户主动提供大致位置、车型编号和将来的准确试驾时间。Agent 先排序取最近五家，再展示模拟试驾车与时段状态；十分钟候选记录在 Agent 数据库中，不保存客户坐标。
4. 客户只能选本次候选中状态为可用的门店。提交时再次读取客户身份和原工单，复查该店的模拟状态与快照编号，用数据库版本条件更新保存门店、车型、时间、客户编号、选择时间与快照编号。重复提交相同选择返回原任务；其他选择、过期、并发版本变化都拒绝。旧建议失效。
5. 管理员重新打开或刷新 Agent 任务后才能继续查政策和顾问，仍要人工确认；模拟选择不能作为真实车源或顾问门店归属的证据。

## 接口与边界

| 接口 | 用途 | 约束 |
|---|---|---|
| `GET /api/agent/customer-stores/csrf` | 客户会话取得短时令牌 | 普通客户、正常状态、有效 Session |
| `GET /api/agent/customer-stores/{taskId}` | 看自己的任务版本和选店状态 | 重新读取原工单并校验 `customerId`、状态快照；不返回管理员资料 |
| `POST /api/agent/customer-stores/{taskId}/offers` | 查询五店并创建十分钟候选 | `expectedVersion`、位置、车型、时间；同源 Origin 与 CSRF；坐标不落库 |
| `POST /api/agent/customer-stores/choices` | 提交 `offerId` 和 `storeId` | 客户本人、本次五家、原本可选、重新查询仍可用且快照相同、版本未变 |

`carSystem` 只收到 `GET /api/user/current` 和 `GET /api/workOrder/get`；选店不发送任何业务写请求。`customerId` 从业务工单 HTTP 响应提取；字段缺失则拒绝，不用页面输入猜测归属。Agent 的 `agent_store_offer` 表只保存候选、客户编号、任务版本、车型、时间和有效期，`agent_task` 保存最终选择元数据。现有表启动时补列，无须修改 `carSystem` 表。

## 已验证与未验证

- 真实 PostgreSQL 隔离探针覆盖：五店候选存取、不可用店与越权拒绝、快照不符与过期拒绝、两个并存候选只有一次选择能写入任务、重复提交幂等、管理员改动清除客户选择、工单状态变化时不写入、业务响应缺 `customerId` 时拒绝。
- HTTP 测试覆盖客户入口的同源 CSRF。Java 21 容器执行 `mvn -q test`：126 例、失败 0、错误 0、跳过 34（需真实数据库或外部服务的用例默认不跑）。此前同一实现的 `mvn -q package` 成功；临时 pgvector 数据库探针：29 例、失败 0、错误 0。三组 Profile 的本机 `8091` 进程重启后健康检查为 `UP`，两个演示页面均返回新版内容；无客户登录或管理员登录态访问客户页面时会显示拒绝。
- 2026-11-02 已用本机模拟测试客户 `agentuser` 与管理员 `agentadmin` 完成双身份联调，细节见下节。C02 主路径另有[离线回放](../../../data/eval/cases/C02-nearby-store-selection.md)；该回放的业务接口、检索和模型均非真实线上调用。
- 选店提交与业务系统读取之间仍有跨系统时间窗；目前没有自动清理过期候选的保留策略。真实分配继续关闭，后续必须先补可信车源、顾问门店归属和分配前复查。

## 2026-11-02 双身份本机联调

两个测试账号通过 `carSystem:8080` 正常登录，业务码均为 `0`；管理员角色为 `2`，客户角色为 `0`。登录响应的 `SESSION` Cookie 属性为 `Domain=localhost`、`Path=/api`、`HttpOnly`、`SameSite=Lax`。HTTP 探针在内存中传递 Cookie 与 CSRF 令牌，不记录其值；脚本所用的通用 Cookie 容器没有接受 `Domain=localhost`，因此 HTTP 探针显式传递登录响应 Cookie，浏览器自动携带另行验证。

现有 17 条待分配试驾工单均不属于模拟客户。客户通过正常 `POST /api/workOrder/add` 新建一条明确标为“仅本地测试”的模拟工单 `65`，没有直接操作 `carSystem` 数据库或修改其代码。管理员为工单创建 Agent 任务 `d24fe2ac-e016-42c4-8b25-7f289b29a9fd`，客户通过 Agent 接口读取本人任务并从最近五家中选择 `STORE-C`；再次提交相同选择返回相同版本 `1`。业务系统重查显示原工单仍是待分配、无顾问。

| 检查 | 实测 |
|---|---|
| 管理员取任务 CSRF、客户取选店 CSRF | 均 HTTP `200` |
| 管理员取客户令牌、客户取管理员令牌 | 均 HTTP `403` |
| 管理员创建任务缺令牌、跨站 `Origin`、客户凭客户令牌创建管理员任务 | 均 HTTP `403` |
| 客户读本人任务、管理员读本人任务 | 均 HTTP `200` |
| 管理员读客户任务、客户读管理员任务 | 均 HTTP `403` |
| 客户创建五店候选缺令牌、跨站 `Origin`、误用管理员令牌 | 均 HTTP `403` |
| 客户使用本会话令牌创建五店候选并选择 `STORE-C` | 均 HTTP `200`；五店顺序 `A/B/C/D/E`，可选 `A/C/E` |
| 选择后重查业务原工单 | HTTP `200`、业务码 `0`、状态 `0`、顾问为空 |

应用内浏览器另行完成 `agentuser` 登录 → 客户页“重新检查” → 输入任务编号 → 显示“已确认工单归属”和“已记录门店 STORE-C · 任务版本 1”。这验证浏览器对 `localhost:8080` 与 `localhost:8091` 自动共享该 Cookie，页面能读取客户任务。随后恢复原有 `agentadmin` 浏览器登录，客户页重新拒绝管理员身份。本次**没有在浏览器重复提交选店**；选店正向写入和 CSRF 反例由独立 HTTP 会话实测。

本次只验证本机模拟身份与数据；没有真实车源、顾问门店归属、真实预约或真实分配。登录口令、Cookie 值与 CSRF 令牌不写入仓库。
